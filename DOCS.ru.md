# taskmark — как он устроен

Рабочая документация для себя: что происходит внутри, в каком порядке, где что лежит и какие
решения приняты сознательно. Английский `README.md` — короткое описание для публикации; здесь
подробности и причины.

---

## 1. Зачем

Не чистить контекст дорого, чистить — значит потерять разбор: какой файл за что отвечает, как
части связаны, что уже пробовали и что не сработало. Плагин закрывает разрыв: замечает переход к
другой задаче, выгружает накопленное в файл и ведёт свою историю расхода токенов (Claude Code
подчищает собственные логи, поэтому статистику надо копить с первого дня).

Три функции, ничего сверх:

1. разметка границ задач;
2. заметка-выгрузка в `.claude/research/` перед потерей контекста;
3. локальная статистика в SQLite + отчёты (этап 2).

Наружу не уходит ничего, кроме двух справочных запросов за тарифами и курсом (см. §8).

## 2. Карта файлов

```
.claude-plugin/plugin.json   манифест плагина (имя, версия, лицензия)
hooks/hooks.json             какие события Claude Code перехватываем
bin/taskmark                 лаунчер для Linux/macOS (правит sys.path и зовёт cli)
bin/taskmark.cmd             то же для Windows (нужен python в PATH)
commands/task-split.md       слэш-команда /task-split
commands/research-save.md    слэш-команда /research-save

taskmark/config.py      пути, пороги по умолчанию, проценты калибровки, аварийный выключатель
taskmark/transcript.py  разбор JSONL Claude Code: ходы, токены, файлы, команды, replay()
taskmark/db.py          схема SQLite, миграции, запись ходов и задач
taskmark/state.py       маленький JSON на сессию (хуки — разные процессы, это их общая память)
taskmark/boundary.py    решение «новая задача или продолжение»
taskmark/embed.py       второй слой: эмбеддинги, резидентная служба с моделью
taskmark/calibrate.py   пороги из собственных данных пользователя, версии критерия
taskmark/research.py    сборка заметки из фактов транскрипта
taskmark/pricing.py     внешние тарифы (LiteLLM) и курс USD→EUR (Frankfurter)
taskmark/report.py      метрики периода и задач, сравнение, разбор причин роста
taskmark/cli.py         обработчики хуков и команды
```

Данные: `~/.claude/taskmark/` (переопределяется `TASKMARK_HOME`)

```
taskmark.db        основная база
state/<session>.json  состояние сессии: открытая задача, файлы окна, ритм пауз, центроид
prices.json, fx.json  кэш тарифов и курса
markers.txt        необязательные свои фразы-маркеры перехода (по умолчанию пусто)
note-words.txt     необязательные свои слова для содержимого заметок
disabled           флаг выключения
taskmark.log       ошибки (хук никогда не роняет сессию — всё пишется сюда)
```

## 3. Поток: что происходит в живой сессии

| Событие Claude Code | Хук | Что делает |
|---|---|---|
| `SessionStart` | `hook session-start` | заводит состояние сессии, пишет событие; закрывает «висящие» задачи других сессий (см. ниже) |
| `UserPromptSubmit` | `hook prompt` | **главное место**: решает про границу, закрывает старую задачу и пишет заметку, открывает новую, обновляет центроид и словарь, кормит калибратор |
| `PostToolUse` (Read/Edit/Write/Grep/Glob/Bash/NotebookEdit) | `hook tool` | собирает пути файлов окна, пополняет словарь задачи именами файлов, проверяет «возврат к прежней задаче» и при необходимости склеивает задачи |
| `PreCompact` | `hook pre-compact` | докачивает ходы в базу и **пишет заметку** — ради этого всё и затевалось |
| `Stop` | `hook stop` | докачивает ходы в базу |
| `SessionEnd` | `hook session-end` | докачивает ходы, закрывает задачу, пишет заметку |

Правила устойчивости:

* любое исключение перехватывается в `cli.main` и пишется в `taskmark.log`, возврат всегда `0` —
  плагин не должен ломать работу;
* `config.is_disabled()` проверяется первой строкой хука: `TASKMARK_OFF=1` или файл `disabled`
  превращают все хуки в пустышки;
* вывод в сессию — только документированный JSON `{"systemMessage": ..., "suppressOutput": true}`
  и только когда реально записана заметка.
* **блокировка состояния сессии** (`state.try_lock`, файл `state/<session>.lock`): `st.load()`
  берёт `flock` и держит его до выхода процесса — хуки и `taskmark mark` короткие процессы, так что
  это ровно их чтение-изменение-запись. Ждёт до `LOCK_WAIT_SECONDS` (30 с), потом идёт без блокировки.
  Зачем: 23.09 хук промпта из очереди прочитал состояние до того, как `mark resume` его сохранил,
  и записал старую задачу поверх — задача #75 осталась открытой навсегда;
* **висящие задачи** (`close_orphans`): если окно/tmux убили, `SessionEnd` не приходит и задача
  остаётся без заметки. На старте любой сессии открытые задачи других сессий моложе 14 дней,
  у которых транскрипт молчит ≥ `ORPHAN_IDLE_SECONDS` (2 ч) и чей lock свободен, закрываются:
  текущая задача той сессии — с заметкой (`boundary: orphan`, конец = последняя активность),
  рассинхронизированная (сессия уже ушла на другую задачу) — только `ended_at` по последнему ходу,
  без переписывания заметки (`orphan-stale`). Не больше 3 за старт.

## 4. Разбор транскрипта (`transcript.py`)

Подход взят у **ccusage** (MIT) — там это решено правильно, изобретать не стали:

* один ход = запись `type: "assistant"` с `message.usage`;
* четыре категории токенов: `input`, `output`, `cache_creation`, `cache_read`;
* новые сборки дробят запись кэша на эфемерные корзины внутри `usage.cache_creation`
  (`ephemeral_5m/1h_input_tokens`) — берём максимум из плоского поля и суммы корзин;
* **дедупликация** по ключу `(message.id, requestId, sessionId)`; из дублей оставляем запись с
  большей суммой токенов, а при расхождении по `isSidechain` — не-подагентскую;
* `context_size = input + cache_read + cache_creation` последнего хода основной цепочки
  (подход **claude-powerline**, MIT; ходы подагентов исключаются);
* если в записи есть собственный `costUSD` — он приоритетнее расчёта по тарифам;
* чтение **инкрементальное**: в `ingest_state` хранится байтовый офсет по каждому файлу, поэтому
  повторный проход читает только хвост; повторная запись безопасна (PK = `request_id`).

Дополнительно из транскрипта достаются: пути файлов из аргументов инструментов
(`paths_from_tool`) и из shell-команд (`paths_from_command`), команды, упавшие команды с текстом
ошибки, человеческие промпты (`origin.kind == "human"`, служебные `<command-message>` отбрасываются).

`replay(path)` отдаёт хронологию «промпт / касание файлов» — ровно те же два входа, что получают
живые хуки. На этом работает офлайн-разметка старой истории (§7).

## 5. Границы задач (`boundary.py`) — ядро

Два слоя, решение **никогда не по одному сигналу**. Фразовые списки были первой попыткой и
выброшены: каждый формулирует переход по-своему и на трёх языках сразу. Осталось то, что смотрит
на структуру работы, а не на слова.

**Жёсткие сигналы** (любого одного достаточно):
* ручная отметка `/task-split`;
* сменилась ветка git;
* очень длинная пауза (`pause_hard`, по умолчанию час);
* **сменилось место работы** (`targets_from_tool` в `transcript.py`): последний ход работал там,
  где задача ещё не была, — другой ssh/scp/rsync-хост, docker-контейнер, kubectl-контекст, хост
  БД (`mysql -h …`) или локальный проект (ближайший предок с `.git`/`pyproject.toml`/`package.json`…).
  Ничего не завязано на конкретные машины. Локальный путь в команде с ssh тоже считается
  (`scp ./app/x host:` задевает и проект, и хост), поэтому шаг деплоя пересекается с задачей
  проекта и границы не даёт. Тела heredoc не разбираются: это данные (скрипт, документация,
  текст коммита), а не команды — первый живой прогон поймал `ssh:host` из текста документации. Срабатывает и в молодой задаче: ошибку поправит Claude (§5a).

**Граница задним числом.** Сигналы «файлы» и «место работы» описывают **прошлый ход**, а не
только что введённый промпт: переход случился на предыдущем сообщении. Если сработали только они
(`turn_based()`), старая задача закрывается моментом предыдущего промпта, новая начинается с него,
его ходы и файлы переносятся (`close_task(until=…)`, `move_turns`).

**Сильные сигналы** (нужны два, либо один сильный + один слабый):
* рабочий каталог ушёл в другое дерево (`cd` внутри проекта — нормальная работа, не граница);
* **каталоги** файлов последнего окна не пересекаются с каталогами задачи. Сравнение точных путей
  было измерено и выброшено: на реальных логах пересечение = 0.00 на 85-м процентиле, сигнал
  срабатывал почти на каждом промпте. Каталоги (сам каталог + родитель) это чинят. Общие для
  всех задач каталоги в сравнение не входят: верхний уровень (`/root`, `/srv`, `/home`, `/opt`…) и
  всё под `.claude` (память, заметки, состояние плагина). Иначе, как показала живая сессия, задача
  про taskmark и задача про переводчик совпадали на 0.62 и сигнал не срабатывал;
* потеря лексической связности: доля слов нового промпта, уже встречавшихся в задаче (прошлые
  промпты + имена задетых файлов), ниже `CONTINUITY_MIN`. Просто пересечение множеств, без
  словарей и модели — одинаково работает для русского, эстонского, английского и кода;
* низкий косинус промпта к центроиду задачи (второй слой, §6).

**Слабые сигналы**:
* пауза, необычная **для ритма этой сессии** (порог = 5 × медиана промежутков, но не меньше
  10 минут) — люди ходят за кофе посреди задачи, сама по себе пауза не граница;
* прошлый ход не тронул ни одного файла — задача выглядела законченной.

Предохранители: задача моложе `MIN_TURNS_BEFORE_SPLIT` (3 промпта) не режется; пересечение файлов
оценивается, только когда обе стороны тронули хотя бы 4 файла; слишком короткие промпты («ок»,
«дальше», «jah») в лексическом сигнале игнорируются.

**Склейка при возврате** (`check_return`): если сразу после раскола снова открываются файлы
прежней задачи (в пределах 2 часов и пока новая задача молодая), раскол признаётся ошибкой —
задачи сливаются, в `tasks.merged_into` проставляется владелец. Отчёты считают только несклеенные.

### 5a. Второе мнение — сам Claude (`model_context`, `taskmark mark`)

Правила не понимают смысла коротких реплик: «покажи нагрузку на сервер» после работы над
плагином по словам и эмбеддингам почти не отличается от продолжения (замерено: 0.30 у настоящих
переходов против 0.35 у продолжений). Claude видит весь разговор и отличает сразу. Поэтому на
каждый промпт хук `UserPromptSubmit` добавляет в контекст одну строку (`additionalContext`):
что решили правила и как возразить. **Молчание = согласие**, продолжение ничего не стоит.

| Claude | правила | итог |
|---|---|---|
| молчит | границы нет | та же задача |
| молчит | граница | граница (Claude согласен) |
| `mark name "<тема>"` | граница (на этом или предыдущем промпте) | согласие, задача получает имя от Claude |
| `mark new "<тема>"` | границы нет | граница на этом промпте — правила её пропустили |
| `mark same` | граница (на этом или предыдущем промпте) | раскол отменяется: задачи сливаются, состояние прежней задачи восстанавливается, её цели пополняются |
| `mark resume "<тема или #id>"` | — | возврат к прежней задаче этой сессии (по `#id` или по словам заголовка/эмбеддингам) |

Каждое возражение пишется событием `model-mark` (`verdict`, `local`, `agree`), сводка — в
`taskmark status` (строка `claude:`). Выключить: `"model_marks": false` в
`~/.claude/taskmark/settings.json`. Команда выполняется через Bash — в режиме с подтверждениями
стоит разрешить её правилом вида `Bash(*/bin/taskmark mark:*)`.

При импорте истории (`ingest --mark`) Claude нет — там работают только правила.

Замеренное поведение на реальной сессии автора (534 промпта, 12 дней): **104 задачи, 5.1 промпта
на задачу**. Причины границ: паузы 48, потеря лексической связности 33, расхождение каталогов 17,
эмбеддинги 5 (плюс 22 раза участвовали вторым сигналом).

## 6. Эмбеддинги (`embed.py`) — второй слой

* Модель: `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, CPU, локально, лениво.
  Очевидная `all-MiniLM-L6-v2` была замерена первой и **не годится**: одно и то же предложение
  по-русски и по-эстонски дало 0.26, а неродственная русская фраза — 0.69; она разделяет алфавиты,
  а не смыслы.
* Сравнивается промпт с **центроидом** последних `CENTROID_PROMPTS` (12) промптов задачи, центроид
  пересчитывается по мере роста задачи.
* Косинусы у таких моделей завышены и порог интуитивно не выбирается — он берётся из собственного
  распределения пользователя (§7).
* Загрузка модели — около 24 с, а каждый хук это новый процесс. Поэтому модель живёт в **резидентной
  службе**: unix-сокет в `state/embed.sock` (на Windows — loopback TCP + `state/embed.port`),
  первый ответ 3.4 с, дальше 18 мс, простой дольше 30 минут — служба выходит (держит ~1.4 ГБ RSS).
  **Одна копия на каталог данных** — эксклюзивная блокировка `state/embed.lock`; сокет открывается
  только после загрузки модели, так что пока модель грузится, хук мгновенно пропускает сигнал.
  Без этого (замерено в первый же день): каждый хук без ответа запускал новую копию, новая
  отбирала сокет у старой — 14 копий и ~19 ГБ памяти.
* **Слой выключен по умолчанию** (`"embeddings": false` в settings.json). За 5 дней реального
  использования он решил примерно одну границу, а держит ~1 ГБ памяти. `taskmark fetch-model`
  скачивает модель (~450 МБ, один раз) и сам ставит `"embeddings": true`.
* **Модель не скачивается сама.** Даже при включённой настройке слой молчит, пока модели нет в
  локальном кэше (`available()` проверяет кэш HF).
* Без `sentence-transformers` плагин работает на одних правилах. `TASKMARK_NO_EMBED=1` выключает
  слой, `TASKMARK_EMBED_INLINE=1` считает в том же процессе (для тестов и разовых импортов).
* Честно: сходство само по себе слабое — против меток, выведенных из правил, оно отделяет
  продолжение от перехода с AUC ≈ 0.6. Именно поэтому одного сигнала никогда не хватает.

## 7. Калибровка (`calibrate.py`) — пороги не константы

Зачем: у человека с пятиминутными промптами и у человека с часовыми «длинная пауза» разная; у того,
кто сидит в одном репозитории, и у того, кто скачет между серверами, разное нормальное пересечение
файлов. Ручные числа подошли бы только тому, кто их подбирал.

Как:

1. каждый промпт кладёт значения своих сигналов в `signal_samples` (`pause`, `file_overlap`,
   `cosine`) — разметка человеком не нужна;
2. после `CALIBRATION_MIN_SAMPLES` = 200 промптов (примерно две недели обычной работы) пороги
   заменяются процентилями собственного распределения: пауза «длинная», если она в верхних 15 %
   пауз этого человека; сходство «потеряно», если оно в нижних 10 %;
3. пересчёт **намеренно редкий**: автоматически — только когда выборка выросла втрое, иначе по
   команде `taskmark calibrate --force`. Критерий, который гуляет, делает периоды несравнимыми;
4. каждая калибровка получает номер версии, каждая задача хранит `calib_version`, под которой была
   размечена. Отчёты периодов с разными версиями не смешивают — предупреждают.

Ручная коррекция необязательна: `/task-split` (граница здесь) и `taskmark same` (это была та же
задача) пишутся в `feedback` и служат подсказкой, не заменой процентилям.

Калибровка на реальных данных автора: пауза мягкая 33 мин / жёсткая 186 мин, пересечение каталогов
≤ 0.04, косинус ≤ 0.25 — близко к зашитым значениям по умолчанию, ровно поэтому они такие.

## 8. Заметки-выгрузка (`research.py`)

Пишутся в `<проект>/.claude/research/ГГГГ-ММ-ДД-slug.md` при закрытии задачи и **перед каждой
компакцией**.

Два предохранителя, включённых по умолчанию:

* **В git заметки не попадают никогда.** При первой записи рядом создаётся
  `.claude/research/.gitignore` со звёздочкой — он прячет и заметки, и сам себя, в любом
  репозитории и не трогая `.gitignore` проекта. Отключается `TASKMARK_NOTES_GIT=1`.
* **Секреты маскируются.** Заметка собирается из настоящей истории команд, а там бывают пароли.
  Весь текст перед записью проходит через `redact()`: `-pПароль`, `--password=`, `token=`,
  `Bearer …`, ключи вида `sk-/hf_/ghp_/rpa_/xai-/AIza`, тела ssh-ключей, ключ в адресе запроса
  (`?key=… &access_token=…`) и в заголовках вида `X-…-Key:`. Правила простые и
  срабатывают с запасом: замаскированная лишняя строка не мешает, утёкший пароль мешает.

**Только свои куски транскрипта.** Если работа ушла в другую задачу и вернулась (`mark resume`),
кусок между ними принадлежит другой задаче. Заметка берёт не весь отрезок «от начала задачи до
конца», а только участки, где ходы в `turns` помечены этой задачей (`db.task_spans`): участок
начинается сразу после чужого хода (там стоит промпт) и кончается последним своим ходом;
ответы модели отбираются точно по `requestId`. В ссылке на транскрипт тогда несколько диапазонов
строк и одна команда `sed -n 'a,bp;c,dp'`. Нет своих ходов — прежнее поведение (весь отрезок).

Собираются из фактов транскрипта, а не из пересказа диалога:

* о чём была задача (первые промпты), период, причина закрытия;
* файлы, которых касались, по частоте;
* команды, которые стоит сохранить;
* **что не сработало** — упавшие команды с текстом ошибки (по опыту это самое ценное);
* решения и открытые вопросы (здесь и только здесь используются словари `FAILURE_MARKERS` /
  `DECISION_MARKERS` и пользовательский `note-words.txt` — на границы задач они не влияют);
* `slugify` умеет кириллицу и эстонские буквы (транслитерация).

`/research-save` — просьба к Claude заполнить такой же файл подробнее, пока контекст ещё цел.
Модель плагин сам не вызывает.

## 8a. Что плагин говорит в сессию (`hints.py`)

Контекст плагин сам не чистит — хуки не умеют запускать `/clear`, и так было задумано. Зато он
делает очистку безопасной и подсказывает, когда её пора сделать:

* **Подсказка на границе.** Если задача закрыта, заметка записана, а контекст больше
  `hint_min_context` (по умолчанию 150k токенов) — одна строка: «прошлая задача сохранена → путь ·
  контекст 472k · /clear безопасен». Меньше порога — молчит. Нет заметки — тоже молчит: нельзя
  говорить «сохранено», если сохранять было нечего.
* **Заметки после очистки.** На `SessionStart` с источником `clear`, `compact` или `startup` в
  контекст добавляется список последних заметок этого проекта (до 8 штук за 14 дней): только пути
  и заголовки, несколько сотен токенов, с указанием читать нужную по делу, а не все сразу. После
  `resume` список не добавляется — там контекст и так цел.
* **Возврат заметки после компакции.** Задача после компакции продолжается, поэтому на
  `SessionStart` с `compact` в контекст кладётся **полный текст** заметки текущей задачи — той, что
  `pre-compact` записал секунду назад (до 12 000 символов, ~3k токенов). Резюме Claude Code
  обычно теряет файлы, команды и провалы — заметка их возвращает. В списке ниже она не
  повторяется. Событие `note-restored`.
* **Замер пользы.** Каждое чтение файла из `.claude/research/` — через `Read` или командой в Bash
  (`cat`, `sed`, `head`… с путём заметки) — пишется событием `note-read`, каждое
  предложение списка — `notes-offered`. `taskmark report` показывает: написано / предложено /
  прочитано. Это и есть проверка через месяц: если «прочитано» стоит на нуле — идею закрыть.

Настройки — `~/.claude/taskmark/settings.json`, всё необязательно:

```json
{"hint_min_context": 150000, "hint_color": null, "offer_notes": true, "offer_max": 8, "offer_days": 14,
 "model_marks": true, "embeddings": false}
```

`hint_color` — `yellow`, `cyan`, `green`, `red`, `magenta`, `blue`, `gray`, `bright-yellow`,
`bright-cyan`. По умолчанию выключен: строку рисует Claude Code, и пропускает ли он ANSI-цвет,
не документировано. Если вместо цвета видны символы вроде `[33m` — вернуть `null`.

## 8b. Привязка к git (`vcs.py`, таблица `task_git`)

Только **локальные репозитории на этой машине**: ни GitHub, ни других внешних сервисов. Работа
по ssh на сервере без git следа здесь не оставляет — у задачи остаются её файлы и цели.

* при **первом касании** файла из репозитория задача запоминает `repo`, `branch`, `head_start`
  (`note_repos` в хуке `tool`; git спрашивается один раз на репозиторий на задачу — хук не
  дорожает);
* при **закрытии** дописываются `head_end`, флаг незакоммиченных изменений и список коммитов
  диапазона (`close_git`); они же уходят в заметку разделом `## Git — <repo> (<branch>)`;
* **обратный поиск**: `taskmark git <sha>` → задача, её время и заметка. Принадлежность
  считается честно (`merge-base --is-ancestor` к `head_end`, но не к `head_start`), поэтому
  коммит, существовавший до задачи, ей не приписывается;
* `taskmark git` без аргумента — последние задачи с диапазонами и числом коммитов.

Все вызовы git обёрнуты таймаутом 3 с и никогда не роняют хук.

## 8c. Журнал решений (`decisions`, `taskmark decide`)

Раздел `## Decisions` в заметке раньше собирался по словам-маркерам и был почти всегда пустым
или мусорным. Угадывать решения по словам не получается, поэтому пишет их **тот, кто решил, в
момент решения** — по той же схеме, что и второе мнение о границах (§5a):

```bash
taskmark decide "<что решили>" --why "<почему>" [--instead "<что отвергли>"] [--who user|claude]
taskmark decisions [--days=90] [текст]     # журнал, новые сверху, с поиском по подстроке
```

* правило записи узкое: **только то, что меняет поведение или архитектуру**, иначе журнал
  превращается в шум;
* таблица `decisions` хранит `who/what/why/instead`, задачу и **коммит репозитория на момент
  решения** — вместе с §8b получается цепочка «решение → задача → коммит → заметка»;
* записанные решения вытесняют старую эвристику в заметке (она осталась запасным вариантом);
* недельный отчёт (`taskmark report`) печатает журнал за период;
* строка-подсказка на промпт выросла со 132 до ~178 токенов; на сессию в 36 промптов это
  ~3 тыс. токенов против 39 млн чтений из кэша — 0.008%.

## 9. База (`db.py`)

| Таблица | Что хранит |
|---|---|
| `turns` | один ход ассистента: время, модель, 4 категории токенов, размер контекста, флаг подагента, `task_id`, `cost_usd` (если был свой). PK `request_id` делает импорт идемпотентным |
| `tasks` | задача: сессия, каталог, начало/конец, заголовок, причина границы, `prompts`, `merged_into`, `note_path`, `calib_version` |
| `task_files` | какие файлы трогала задача и сколько раз |
| `events` | журнал: `prompt`, `boundary`, `note`, `merge`, `calibration` |
| `signal_samples` | сырые значения сигналов для калибровки |
| `calibration` | версии критерия и их параметры |
| `feedback` | ручные коррекции |
| `ingest_state` | байтовый офсет по каждому транскрипту |

Миграции аддитивные: `CREATE TABLE IF NOT EXISTS` не трогает существующую таблицу, поэтому список
`ADDED_COLUMNS` добавляет недостающие колонки через `ALTER TABLE` при каждом подключении. База от
старой версии не падает, а расширяется.

## 10. Этап 2: деньги и метрики (`pricing.py`, `report.py`)

**Тарифы не зашиты.** Таблица LiteLLM `model_prices_and_context_window.json` (та же, что у ccusage)
даёт четыре ставки на модель: ввод, вывод, запись в кэш, чтение из кэша. Кэш на диске, TTL 7 дней;
курс USD→EUR — Frankfurter (ставки ЕЦБ), TTL сутки, можно прибить через `TASKMARK_EUR_PER_USD`.
Нет сети и нет кэша — стоимость показывается как неизвестная: неверное число хуже отсутствующего.
(Мелочь из практики: Frankfurter отдаёт 403 на стандартный User-Agent urllib, поэтому запрос идёт
со своим заголовком.)

**Метрики периода:**

* токены по четырём категориям и стоимость;
* доля попаданий в кэш `cache_read / (cache_read + cache_creation + input)`;
* отношение выхода ко входу;
* доля подагентов (по токенам ходов с `isSidechain`);
* средний размер контекста, ходов на задачу, стоимость на задачу.

**Сравнение** со скользящим предыдущим периодом (по умолчанию втрое длиннее) и разбор причин роста
стоимости задачи — ровно четыре, и только те, что подтверждаются числами:

| Что видно | Вывод |
|---|---|
| сдвинулось отношение выход/вход, ходов на задачу столько же | сменилась модель или режим усилий |
| сдвинулось число ходов на задачу | изменился способ работы (промпты, инструменты, объём) |
| упала доля кэш-хитов | кэш ломается (контекст правится рано, сессии часто перезапускаются) |
| вырос средний контекст | контекст накапливается, стоит чистить раньше |

Два правила, без которых отчёт уверенно врёт: периоды с разными версиями калибровки не
сравниваются, а период с менее чем `MIN_TASKS_FOR_TREND` = 8 задачами показывается как «мало
данных», а не как тренд.

**Офлайн-разметка истории.** `ingest` сам по себе даёт ходы, но не задачи, и метрики «на задачу»
были бы пустыми недели. Поэтому `ingest --mark` прогоняет старые транскрипты через те же правила
границ (`--embed` добавляет слой эмбеддингов на время импорта) и привязывает импортированные ходы
к задачам по времени внутри сессии. На своей истории: 20 508 ходов, 398 задач.

## 11. Команды

```bash
python3 -m taskmark.cli status              # что накоплено, активная калибровка, где база
python3 -m taskmark.cli ingest [--mark] [--embed]   # импорт прошлых сессий (и разметка задач)
python3 -m taskmark.cli report [--days=7]   # метрики периода + самые тяжёлые задачи
python3 -m taskmark.cli cost [--days=30]    # стоимость по дням
python3 -m taskmark.cli split               # следующий промпт начинает новую задачу
python3 -m taskmark.cli same                # отменить последний раскол (это была та же задача)
python3 -m taskmark.cli mark new|same|resume|name ["тема"] --session ID   # мнение Claude (§5a)
python3 -m taskmark.cli git [<sha>]         # диапазоны репозиториев по задачам; чей это коммит
python3 -m taskmark.cli note                # написать заметку по открытой задаче прямо сейчас
python3 -m taskmark.cli calibrate [--force] # пересчитать пороги по своим данным
python3 -m taskmark.cli fetch-model         # скачать модель эмбеддингов (только вручную)
python3 -m taskmark.cli off / on            # аварийный выключатель, данные сохраняются
python3 -m taskmark.cli embed-daemon        # служба с моделью (поднимается сама)
```

В сессии: `/task-split`, `/research-save`.

Переменные окружения: `TASKMARK_HOME`, `TASKMARK_OFF`, `TASKMARK_NO_EMBED`, `TASKMARK_EMBED_MODEL`,
`TASKMARK_EMBED_INLINE`, `TASKMARK_EUR_PER_USD`, `TASKMARK_QUIET`, `TASKMARK_KEEP_SCRATCH`,
`TASKMARK_NOTES_GIT`.

### Стоимость хуков (замерено)

| хук промпта | 0.14 с | хук инструмента | 0.09 с |
|---|---|---|---|
| `stop` на транскрипте 255 МБ | 1.8 с холодный / 0.09 с инкрементальный | заметка перед компакцией | 1.1 с |
| 12 хуков параллельно | 0.16 с, ошибок 0 | выключенный плагин | 0.06 с |

Изначально хук промпта занимал 4.2 с: `available()` проверял библиотеку обычным импортом, а он
тянет torch. Теперь `find_spec` — 0 мс. Лог обрезается на 1 МБ (одна старая копия `.log.1`).

## 12. Проверка парсера

Свой подсчёт сверялся с внутренним счётчиком Claude Code (`cost-state` в транскрипте). Важно, что
`cost-state` — снимок за текущий **запуск** сессии (от `startTime`), а не за весь файл; при сверке
на один и тот же момент и с дедупликацией запись кэша совпала точно, остальные категории — в
пределах 0.4–3 %. Первое расхождение «в 2–23 раза» было нашей ошибкой сравнения окон, а не парсера.

## 13. Чего плагин не делает

Нет веб-интерфейса, дашборда, облака, локальной генеративной модели, поддержки других клиентов.
Контекст сам не чистит — максимум подскажет. Наружу уходят только два справочных запроса (тарифы и
курс), промпты и файлы не покидают машину.
